1. Перепідключення

Мережа рано чи пізно обірветься: Wi-Fi, тунель, засинання ноутбука. Клієнт має сам відновлювати з'єднання. Socket.io робить це з коробки з наростаючою затримкою (exponential backoff); для сирого WebSocket — пишеш вручну. 

// «сирий» WebSocket: простий reconnect з backoff
function connect() {
  const ws = new WebSocket(url);
  let delay = 1000;
  ws.onopen = () => { delay = 1000; };
  ws.onclose = () => {
    setTimeout(connect, delay);
    delay = Math.min(delay * 2, 30000); // 1s, 2s, 4s … до 30s
  };
  return ws;
}

2. Heartbeat: виявити «мертве» з'єднання

TCP-з'єднання може «мовчки» померти — сокет ще OPEN, а даних уже не буде. Тому сторони обмінюються ping/pong: якщо на ping довго немає відповіді — вважаємо з'єднання втраченим і перепідключаємось. Socket.io й ws мають вбудований heartbeat; при своєму протоколі роби його сам.

Без heartbeat застосунок «думає», що онлайн, а насправді нічого не отримує. Heartbeat + reconnect — обовʼязкова пара для стабільного реалтайму.

3. Доставка й пропущені повідомлення

Поки клієнт був офлайн, події могли статися. Варіанти гарантій:

  • at-most-once — надіслали й забули (можна втратити); підходить для ефемерного (курсор, «друкує…»);
  • at-least-once — з підтвердженням (ack) і повтором; можливі дублікати — роби обробку ідемпотентною;
  • дозавантаження — при reconnect клієнт питає «дай усе після lastId» — історію добираємо звичайним HTTP-запитом. 
socket.on('connect', async () => {
  const missed = await fetch(`/api/messages?after=${lastSeenId}`).then((r) => r.json());
  missed.forEach(render); // добрали пропущене, далі — жива стрічка
});

4. Backpressure і обсяг

Якщо сервер шле швидше, ніж клієнт встигає, буфери ростуть. Стратегії: throttle/debounce швидких подій (позиція курсора — не частіше ніж раз на 50 мс), обʼєднання оновлень у батч, надсилання дельт замість повного стану. Стеж за ws.bufferedAmount, щоб не переповнити канал.

5. Ще раз: SSE чи WebSocket

  • SSE — лише сервер→клієнт, простий, поверх HTTP, авто-reconnect і Last-Event-ID; менше інфраструктури;
  • WebSocket — двобічний, низька затримка, але треба самому дбати про reconnect/heartbeat/масштабування (або брати Socket.io).

Не ускладнюй завчасно: якщо потрібен лише потік сервер→клієнт — SSE зазвичай достатньо й дешевше в експлуатації. WebSocket вмикай, коли двобічність реально потрібна.

6. Керовані сервіси

Тримати власний WebSocket-кластер (sticky sessions, Redis, автоскейл) — робота. Часто вигідніше взяти керований realtime: Pusher, Ably, Supabase Realtime. Вони дають канали, presence і масштабування як сервіс — ти лише публікуєш і підписуєшся. 

// приклад: Supabase Realtime — підписка на зміни таблиці
supabase.channel('room:1')
  .on('postgres_changes', { event: 'INSERT', schema: 'public', table: 'messages' },
      (payload) => render(payload.new))
  .subscribe();

7. Чеклист продакшену

  • wss:// (TLS) завжди; автентифікація при підключенні;
  • reconnect із backoff + heartbeat;
  • дозавантаження пропущеного через lastId;
  • ідемпотентна обробка при at-least-once;
  • throttle частих подій, надсилання дельт;
  • масштабування: Redis-adapter + sticky sessions (або керований сервіс).
