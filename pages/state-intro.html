1. Проблема «прокидування» пропсів

Коли стан потрібен багатьом компонентам на різній глибині, його доводиться передавати пропсами через проміжні компоненти, яким він не потрібен. Це prop drilling — код стає громіздким і крихким.

// user проходить через App → Layout → Header лише щоб дійти до Avatar
<App> → <Layout user={user}> → <Header user={user}> → <Avatar user={user} />

2. Context — і його межі

Context (з розділу React) вирішує prop drilling, але не створений як повноцінне сховище: будь-яка зміна значення перемальовує усіх споживачів, а логіку оновлення доводиться писати самому. Для складного стану цього замало.

Context ідеальний для рідкозмінних даних (тема, мова, поточний користувач). Для стану, що часто змінюється й читається багатьма компонентами, беруть спеціальну бібліотеку — Zustand чи Redux Toolkit.

3. Спершу — який це стан

Перш ніж тягнути бібліотеку, спитай себе, який це стан:

  • Серверний (дані з API) — це TanStack Query, а не глобальне сховище.
  • Клієнтський глобальний (кошик, тема, автентифікація, UI-стан) — ось тут і потрібні Zustand / Redux.

4. Два підходи

  • Zustand — мінімалістичний: маленький стор-хук, майже без бойлерплейту. Швидкий старт, ідеальний для більшості застосунків.
  • Redux Toolkit — офіційний, структурований стандарт для великих застосунків: передбачувані оновлення, потужні devtools, усталені патерни.

Не додавай глобальне сховище «про запас». Багато застосунків чудово живуть на useState + Context + TanStack Query. Бібліотеку керування станом бери, коли з'явився справді складний спільний клієнтський стан.
