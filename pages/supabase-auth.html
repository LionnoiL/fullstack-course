1. Інший підхід: BaaS

Auth.js — бібліотека у твоєму застосунку. Supabase — це Backend-as-a-Service: хмарна платформа з PostgreSQL, авторизацією, сховищем і API «з коробки». Supabase Auth сам зберігає користувачів і видає токени, а ти лише викликаєш його SDK з клієнта чи сервера.

Ключова відмінність від Auth.js: користувачі й сесії живуть на боці Supabase (таблиця auth.users), а не у твоїй базі. Supabase використовує JWT + refresh-токен і тісно інтегрований із доступом до даних (RLS, нижче).

2. Ініціалізація клієнта

npm install @supabase/supabase-js
// lib/supabase.ts
import { createClient } from '@supabase/supabase-js';

export const supabase = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY, // публічний ключ — безпечно на клієнті
);

anon key призначений для браузера й безпечний, бо доступ обмежує RLS. А ось service_role key — усевладний, тільки для сервера, ніколи в клієнтський код.

3. Реєстрація та вхід (email + пароль)

// реєстрація
const { data, error } = await supabase.auth.signUp({
  email: 'ann@mail.com',
  password: 'super-secret',
});

// вхід
const { error } = await supabase.auth.signInWithPassword({
  email: 'ann@mail.com',
  password: 'super-secret',
});

// вихід
await supabase.auth.signOut();

Supabase сам хешує паролі, надсилає лист підтвердження й керує токенами — писати bcrypt уже не треба.

4. Вхід через OAuth

Той самий OAuth-потік, що ми розбирали, — але одним викликом:

await supabase.auth.signInWithOAuth({
  provider: 'github',
  options: { redirectTo: 'https://myapp.com/auth/callback' },
});

5. Сесія та її відстеження

Поточну сесію/користувача читають так, а на зміни (вхід, вихід, оновлення токена) підписуються через onAuthStateChange:

const { data: { user } } = await supabase.auth.getUser();

supabase.auth.onAuthStateChange((event, session) => {
  // 'SIGNED_IN' | 'SIGNED_OUT' | 'TOKEN_REFRESHED' ...
  console.log(event, session?.user?.email);
});

SDK сам оновлює access-токен за допомогою refresh-токена у фоні — тобі не треба стежити за терміном дії.

6. RLS: авторизація на рівні БД

Найсильніша сторона Supabase — Row Level Security: правила доступу описуються прямо в PostgreSQL. Навіть якщо клієнт звернеться до таблиці напряму, БД віддасть лише дозволені рядки.

-- користувач бачить тільки свої нотатки
create policy "own notes"
  on notes for select
  using ( auth.uid() = user_id );

RLS переносить авторизацію ближче до даних: auth.uid() — це id залогіненого користувача з JWT. Так навіть при помилці в коді клієнта чужі дані не витечуть.

7. Коли що обирати

  • Auth.js — свій бек, повний контроль, хочеш тримати користувачів у власній БД;
  • Supabase — швидкий старт, auth + БД + realtime разом, менше свого бекенду;
  • Clerk/Auth0 — платні платформи з готовим UI й адмінкою (коротко в наступному уроці).
