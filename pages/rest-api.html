1. REST API

Сервер — комп'ютер зі спеціальним програмним забезпеченням. Контролем за роботою сервера займається системний адміністратор.

Дата-центр - спеціально обладнаний майданчик з цілодобовою технічною підтримкою для розміщених серверів. Забезпечує їх безперебійну роботу.

Бекенд - програма, розташована на сервері і здатна обробити вхідні HTTP-запити і має набір готових дій на певні запити.

API (інтерфейс прикладного програмування) — набір чітко визначених правил зв'язку між різними програмними компонентами. Інтерфейс описує, що можна попросити програму зробити і що вийде в результаті.

REST (representational state transfer) — стиль бекенд-архітектури, заснований на наборі принципів, які описують як мережеві ресурси визначаються і адресуються.

REST API — бекенд побудований за принципом REST. Служить прошарком між веб-додатком і базою даних. Має стандартний інтерфейс для звернення до ресурсів. Працює як веб-сайт, ми посилаємо HTTP-запит з клієнта на сервер, а у відповідь, замість HTML-сторінки отримуємо дані в JSON-форматі.

2. Формат запиту

REST-сервіс вимагає, щоб клієнт робив запит на додавання, вилучення або зміну даних. Запит зазвичай складається з:

  • HTTP-метод — визначає, яку операцію виконувати.
  • Заголовок — дозволяє клієнту передавати інформацію про запит.
  • Шлях — шлях до ресурсу. Доступні шляху описуються в документації бекенда.
  • Тіло — додатковий блок запиту, що містить дані.

2.1. HTTP-методи

Виділяють 4 основні методи для роботи з REST-сервісом.

  • POST — створити новий ресурс.
  • GET — отримати набір ресурсів або певний ресурс за ідентифікатором.
  • PUT або PATCH — оновлення певного ресурсу за ідентифікатором.
  • DELETE — видалення певного ресурсу за ідентифікатором.

2.2. Заголовки

Заголовки містять службову інформацію, що відноситься до користувача або контенту запиту, і як клієнт збирається обробляти надану йому інформацію.

Наприклад, тип контенту, який клієнт може обробити у відповіді від сервера (заголовок Accept) або який описує тип ресурсу, який клієнт відправляє серверу або сервер відправляє клієнту (заголовок Content-Type).

MIME-типи — варіанти типів контенту. Використовується для вказівки вмісту запиту і відповіді, складаються з типу і підтипу, які розділені косою рискою /.

Наприклад, текстовий файл, що містить HTML, буде описаний типом text/html. Якщо файл містить CSS, він буде описаний як text/css. Дані в форматі JSON будуть описані як application/json. Якщо клієнт очікує text/css, а отримує application/json, він не зможе розпізнати й обробити контент.

2.3. Шляхи

Запити повинні містити шлях до ресурсу, над яким виконується операція. Доступні шляху (ендпоінти, ресурси) описуються в документації бекенда.

https://bookstore.com/api/orders/289

Такий шлях явно вказує ресурс, навіть якщо ви його ніколи раніше не бачили, тому що він є ієрархічним і описовим. Ми звертаємося до замовлення з ідентифікатором 289.

2.4. Коди відповідей

На запит клієнта, сервер відправляє відповідь. Відповідь містить код стану, щоб інформувати клієнта про результат операції. Коди діляться на групи.

  • 1XX — несуть інформаційне призначення
  • 2XX — коди успішного проведення операції
  • 3XX — описують все, що пов'язано з перенаправленням
  • 4XX — вказують на помилки клієнта
  • 5XX — вказують на помилки на стороні сервера

Не потрібно пам'ятати кожен код стану (їх багато), але необхідно знати найбільш поширені і їх значення.

  • 200 (OK) - стандартна відповідь для успішних HTTP-запитів
  • 201 (Created) - стандартна відповідь для HTTP-запиту, який привів до успішному створенню ресурсу
  • 400 (Bad Request) - запит не може бути опрацьований через невірний
    синтаксис запиту або іншої помилки клієнта.
  • 401 (Unauthorized) - для доступу до ресурсу необхідно ввійти в систему.
  • 403 (Forbidden) - у клієнта немає дозволу на доступ до цього ресурсу.
  • 404 (Not Found) - в даний час ресурс не знайдений. Можливо, він був
    знищений або ще не існує.
  • 500 (Internal Server Error) - загальна відповідь на непередбачений збій, сервера, якщо немає більш конкретної інформації.

3. Запит-Відповідь

Припустимо, у нас є програма, яка дозволяє переглядати, створювати, редагувати і видаляти клієнтів і замовлення невеликого книжкового магазину, бекенд якого розміщений на bookstore.com/api. Використовуючи отримані знання ми можемо, псевдокодом, описати процес запит-відповідь до бекенду.

Якби ми хотіли подивитися всіх клієнтів, запит буде виглядати так.

GET bookstore.com/api/customers
Accept: application/json

Відповідь сервера.

Status: 200 OK
Content-Type: application/json
Body: JSON-дані про всіх клієнтів

Для перегляду одного клієнта ми вказуємо його ідентифікатор.

GET bookstore.com/api/customers/289
Accept: application/json

Відповідь сервера.

Status: 200 OK
Content-Type: application/json
Body: JSON-дані про клієнта

Створення нового клієнта.

POST bookstore.com/api/customers
Content-Type: application/json
Body: { "name": "Mango", "email": "[email protected]" }

Сервер додає унікальний ідентифікатор для цього об'єкта і повертає його назад клієнту.

Status: 201 Created
Content-type: application/json
Body: { "id": 18674, "name": "Mango", "email": "[email protected]" }
