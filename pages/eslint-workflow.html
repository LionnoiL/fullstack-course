1. Інтеграція з редактором

Найзручніше — бачити помилки й форматувати прямо під час набору. У VS Code постав розширення ESLint і Prettier — Code formatter та ввімкни форматування при збереженні: 

// .vscode/settings.json
{
  "editor.formatOnSave": true,
  "editor.defaultFormatter": "esbenp.prettier-vscode",
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  }
}

Тепер збереження файлу автоматично форматує його Prettier і виправляє те, що може, ESLint. Файл .vscode/settings.json кладуть у репозиторій — і в усіх однаково.

2. Git-хуки: перевірка перед комітом

Щоб у репозиторій не потрапляв неохайний код, ставлять хук pre-commit через Husky: 

npm install -D husky
npx husky init   // створить .husky/pre-commit

3. lint-staged — лише змінені файли

Перевіряти весь проєкт на кожен коміт довго. lint-staged запускає інструменти лише на файлах, доданих у коміт. 

npm install -D lint-staged
// package.json
"lint-staged": {
  "*.{js,ts}": ["eslint --fix", "prettier --write"],
  "*.{css,scss,json,md}": ["prettier --write"]
}
// .husky/pre-commit
npx lint-staged

Зв'язка Husky + lint-staged — стандарт де-факто: код автоматично чиститься на кожному коміті, і в історію потрапляє лише охайне. Розробнику не треба нічого пам'ятати — хук спрацьовує сам.

4. Перевірка в CI

Хуки можна обійти (git commit --no-verify), тож остання лінія захисту — CI. Додай крок перевірки в pipeline (напр. GitHub Actions): 

# .github/workflows/ci.yml (фрагмент)
- run: npm ci
- run: npm run lint
- run: npx prettier . --check

Якщо лінт або форматування не проходять — збірка «падає», і проблемний код не потрапляє в основну гілку.
