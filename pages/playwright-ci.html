1. Codegen — тест «під запис»

Не обовʼязково писати кожен локатор руками. Codegen відкриває браузер, записує твої кліки й уведення і генерує код тесту з правильними локаторами — чудовий старт, який потім чистиш.

npx playwright codegen http://localhost:5173

2. Дебаг

npx playwright test --ui          # UI-режим: крокуй тестом, дивись стан
npx playwright test --debug       # покроковий дебаг з інспектором
npx playwright show-trace trace.zip  # розбір падіння постфактум

У коді можна поставити паузу, що відкриває інспектор:

await page.pause(); // застосунок «завмре», відкриється Playwright Inspector

Зв'язка codegen (написати) + UI-режим (дебажити) + trace viewer (розібрати падіння в CI) покриває майже всі потреби. З ними E2E перестають бути «чорною скринькою».

3. Запуск у CI (GitHub Actions)

Найбільша користь від E2E — коли вони ганяються автоматично на кожен push/PR і не пускають зламаний код у гілку. Генератор проєкту вміє створити workflow; ось його суть:

# .github/workflows/playwright.yml
name: Playwright Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps  # браузери + системні залежності
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: playwright-report/

У CI playwright install --with-deps обовʼязковий — він доставляє системні бібліотеки для браузерів. HTML-звіт і трейси зберігай як артефакти, щоб розібрати падіння, не відтворюючи їх локально.

4. Повтори й паралельність

E2E інколи падають через мережеві дрібниці. Розумні повтори в CI відсіюють випадкові збої, не ховаючи справжні баги:

// playwright.config.ts
export default defineConfig({
  retries: process.env.CI ? 2 : 0, // повтори лише в CI
  workers: process.env.CI ? 2 : undefined,
  reporter: 'html',
});

5. Найкращі практики

  • покривай E2E ключові шляхи (вхід, оплата, оформлення), а деталі — unit-ами;
  • шукай за роллю/текстом, не за CSS-класами; уникай waitForTimeout;
  • роби тести незалежними — кожен готує свій стан і не залежить від порядку;
  • мокай зовнішні сервіси для стабільності; сесію логіну зберігай через storageState;
  • став E2E у CI на кожен PR — саме там вони окупаються.
