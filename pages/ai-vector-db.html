1. Навіщо окрема БД

Звичайна БД шукає за точним збігом (WHERE title = '...'). Для RAG нам потрібен інший пошук — за близькістю векторів: «дай 5 чанків, найсхожіших за змістом на цей запит». Це вміють векторні бази: вони індексують embeddings і швидко знаходять найближчі сусіди навіть серед мільйонів записів.

2. Два поширені варіанти

  • pgvector — розширення для PostgreSQL. Вектори живуть поряд зі звичайними даними; не треба окремого сервісу. Ідеально, якщо вже маєш Postgres (зокрема Supabase);
  • Pinecone — керований хмарний векторний сервіс. Береш на себе менше інфраструктури, масштабування — з коробки; підходить для великих обсягів.

Правило: вже є Postgres → бери pgvector (один інструмент, транзакції, JOIN-и з іншими таблицями). Величезні обсяги або не хочеш адмініструвати індекс → керований сервіс на кшталт Pinecone.

3. pgvector: зберігання й пошук

Вмикаємо розширення, додаємо колонку типу vector (розмірність = довжина embedding) і шукаємо за оператором відстані:

create extension if not exists vector;

create table docs (
  id bigserial primary key,
  content text,
  embedding vector(1536)   -- розмірність під модель embedding
);

-- пошук топ-5 найближчих (<=> — косинусна відстань)
select content
from docs
order by embedding <=> $1   -- $1 = embedding запиту
limit 5;

4. Запис embeddings із коду

// індексація: для кожного чанка рахуємо embedding і зберігаємо
for (const chunk of chunks) {
  const { embedding } = await embed({
    model: openai.embedding('text-embedding-3-small'),
    value: chunk.text,
  });
  await sql`insert into docs (content, embedding)
            values (${chunk.text}, ${JSON.stringify(embedding)})`;
}

5. Pinecone: пошук

У Pinecone дані лежать як записи з id, values (вектор) і metadata. Пошук — query з вектором запиту:

import { Pinecone } from '@pinecone-database/pinecone';

const index = new Pinecone().index('docs');

const result = await index.query({
  vector: queryEmbedding,
  topK: 5,
  includeMetadata: true, // дістати текст/джерело з метаданих
});
const chunks = result.matches.map((m) => m.metadata.text);

6. Метадані й фільтри

Разом із вектором зберігай метадані: назву документа, розділ, дату, права доступу. Це дає дві важливі речі:

  • джерела у відповіді («згідно з розділом Х…»);
  • фільтрацію перед пошуком — напр. шукати лише в документах цього користувача чи мовою запиту (аналог WHERE поверх векторного пошуку).

7. Нюанси продакшену

  • та сама модель embedding для індексації й запиту — інакше вектори непорівнянні;
  • оновлення даних — при зміні документа переіндексовуй його чанки;
  • вартість — embeddings рахуються один раз при індексації, далі лише пошук;
  • приватність — не індексуй у зовнішній сервіс те, що не можна віддавати;
  • оцінка — міряй, чи retrieval справді дістає потрібні чанки; від цього залежить якість більше, ніж від вибору моделі.

Пригадай Supabase з розділу Auth: він дає Postgres із pgvector з коробки — зручний старт для RAG у фулстек-проєкті без окремого векторного сервісу.
