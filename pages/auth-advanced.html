1. Access- vs refresh-токени

Access-токен роблять короткоживучим (напр. 15 хв): якщо його вкрадуть, вікно шкоди мале. Але не змушувати ж користувача логінитися щочверть години — тож поряд видають refresh-токен з довгим строком, яким тихо отримують новий access.

  • access_token — короткий, шлеться з кожним запитом до API;
  • refresh_token — довгий, зберігається безпечно й використовується лише для оновлення access.

Auth.js і Supabase роблять оновлення автоматично. Знати механізм усе одно варто: так ти розумієш, чому сесія «живе» довше за access-токен і де може піти не так.

2. Ротація refresh-токенів

Сучасна практика — rotation: при кожному оновленні видається новий refresh-токен, а старий негайно анулюється. Якщо той самий refresh використали двічі — це ознака крадіжки, і вся сесія відкликається. Supabase застосовує ротацію з коробки.

3. Де зберігати токени (найважливіше)

  • httpOnly-cookie — рекомендовано: JavaScript до неї не має доступу, тож XSS не вкраде токен. Додай Secure і SameSite;
  • localStorage — зручно, але вразливо до XSS: будь-який сторонній скрипт прочитає токен. Уникай для чутливих токенів. 
// приклад безпечної cookie на сервері
res.cookie('session', token, {
  httpOnly: true,   // недоступна для document.cookie
  secure: true,     // лише через HTTPS
  sameSite: 'lax',  // захист від CSRF на крос-сайт запитах
  maxAge: 60 * 60 * 1000,
});

Компроміс безпеки: XSS б'є по localStorage, CSRF б'є по cookie. Тому cookie роблять httpOnly + SameSite, а застосунок захищають від XSS (екранування, CSP). Auth.js зберігає сесію саме в захищеній cookie.

4. CSRF коротко

CSRF — чужий сайт змушує браузер надіслати запит із твоєю cookie. Захист: атрибут SameSite на cookie, CSRF-токени для форм (Auth.js додає їх сам) і перевірка Origin. Для суто токен-API (Authorization-заголовок, не cookie) CSRF менш актуальний.

5. Ролі та права (RBAC)

Автентифікація сказала хто — авторизація вирішує що можна. Роль зручно покласти в токен/сесію (як у колбеках Auth.js) і перевіряти на сервері перед дією: 

// server action / route
const session = await auth();
if (session?.user?.role !== 'admin') {
  throw new Error('Немає прав'); // 403
}
await deletePost(id);

Перевірку прав роби на сервері, а не лише ховаючи кнопки в UI. Приховати кнопку — це зручність; захист — це серверна перевірка на кожній чутливій дії.

6. Готові платформи: Clerk, Auth0

Якщо не хочеться будувати навіть сторінки входу — є платні платформи Clerk та Auth0: готові UI-компоненти входу/реєстрації, керування користувачами, MFA, організації/команди. Швидко й надійно, ціна — вендор-лок і оплата за користувачів.

7. Чеклист безпеки автентифікації

  • паролі — лише хеш (bcrypt/argon2), ніколи у відкритому вигляді;
  • секрети (client_secret, service_role) — тільки на сервері й у .env;
  • токени — у httpOnly+Secure+SameSite cookie;
  • короткий access + refresh із ротацією;
  • усе тільки через HTTPS; перевірка прав — на сервері;
  • не винаходити криптографію — використовувати перевірені бібліотеки.
