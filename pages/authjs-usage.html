1. Читання сесії на сервері

У серверному компоненті (Next.js App Router) сесію дістаємо викликом auth(). Якщо користувач не залогінений, повернеться null.

// app/page.tsx — серверний компонент
import { auth } from '@/auth';

export default async function Home() {
  const session = await auth();
  if (!session) return <p>Ти не увійшов</p>;
  return <p>Привіт, {session.user?.name}!</p>;
}

2. Сесія в клієнтських компонентах

Для клієнтських компонентів є хук useSession — але він потребує SessionProvider угорі дерева.

'use client';
import { SessionProvider, useSession } from 'next-auth/react';

function Profile() {
  const { data: session, status } = useSession();
  if (status === 'loading') return <p>Завантаження…</p>;
  if (!session) return <a href="/login">Увійти</a>;
  return <p>{session.user?.email}</p>;
}

У серверних компонентах віддавай перевагу auth() — менше клієнтського JS і жодного «мерехтіння» стану входу. useSession — коли інтерактив справді на клієнті.

3. Захист роутів через middleware

Щоб закрити цілі ділянки сайту (напр. /dashboard), використовують middleware.ts у корені проєкту. Він виконується до рендера сторінки.

// middleware.ts
export { auth as middleware } from '@/auth';

export const config = {
  matcher: ['/dashboard/:path*', '/settings/:path*'],
};

Тонший контроль — через authorized-колбек: пускати лише залогінених, інакше редіректити на сторінку входу:

// auth.ts
callbacks: {
  authorized({ auth, request }) {
    const isLoggedIn = !!auth?.user;
    const isOnDashboard = request.nextUrl.pathname.startsWith('/dashboard');
    if (isOnDashboard) return isLoggedIn; // false → редірект на логін
    return true;
  },
},

4. Колбеки jwt і session

Колбеки дають змогу покласти в токен/сесію додаткові дані — наприклад роль користувача. jwt виконується при створенні/оновленні токена, session — коли клієнт читає сесію.

callbacks: {
  async jwt({ token, user }) {
    if (user) token.role = user.role; // при вході додаємо роль у токен
    return token;
  },
  async session({ session, token }) {
    if (session.user) session.user.role = token.role; // прокидаємо в сесію
    return session;
  },
},

Саме тут «зшивається» автентифікація з авторизацією: провайдер сказав хто користувач, а роль із твоєї БД визначає, що йому можна. Далі перевіряєш session.user.role у сторінках і server actions.

5. Зберігання користувачів (adapter)

За замовчуванням Auth.js тримає сесію в cookie й не пише в БД. Якщо треба зберігати користувачів і сесії у своїй базі — підключають adapter (Prisma, Drizzle, Supabase):

import { PrismaAdapter } from '@auth/prisma-adapter';
import { prisma } from '@/lib/prisma';

export const { handlers, auth } = NextAuth({
  adapter: PrismaAdapter(prisma),
  providers: [GitHub],
});
