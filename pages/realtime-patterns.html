1. Розсилка: кому надсилати

У реалтайм-застосунках ключове питання — кому адресувати подію. Socket.io дає кілька варіантів:

io.emit('e', data);                 // усім підключеним
socket.broadcast.emit('e', data);   // усім, крім відправника
io.to('room1').emit('e', data);     // усім у кімнаті
socket.to('room1').emit('e', data); // у кімнаті, крім відправника
io.to(userSocketId).emit('e', data);// конкретному сокету

2. Кімнати як канали підписки

Кімнати — універсальний механізм підписки. Один сокет може бути в багатьох кімнатах: приватний чат chat:42, дошка board:7, персональний канал user:99 для сповіщень саме цьому користувачу.

socket.join(`user:${userId}`);      // особистий канал
socket.join(`board:${boardId}`);    // спільний ресурс
// сповістити конкретного користувача з будь-якого місця коду:
io.to(`user:${userId}`).emit('notification', payload);

3. Автентифікація сокета

WebSocket не має заголовків на кожне повідомлення — тож токен передають під час підключення й перевіряють у middleware. Далі сокет уже «знає» користувача.

// клієнт
const socket = io('/', { auth: { token } });

// сервер — middleware до з'єднання
io.use((socket, next) => {
  try {
    socket.data.user = jwt.verify(socket.handshake.auth.token, process.env.JWT_SECRET);
    next();
  } catch {
    next(new Error('unauthorized'));
  }
});

Перевіряй права на сервері для кожної дії, а не лише при підключенні. Клієнт може надіслати будь-яку подію — довіряти socket.data.user (з перевіреного токена), а не полям із самого повідомлення.

4. Presence: хто онлайн і «друкує…»

Presence — відстеження активних користувачів. Базовий підхід — оновлювати список на connection/disconnect і розсилати його кімнаті:

const online = new Set();

io.on('connection', (socket) => {
  online.add(socket.data.user.id);
  io.emit('presence', [...online]);

  socket.on('typing', (room) => socket.to(room).emit('typing', socket.data.user.id));

  socket.on('disconnect', () => {
    online.delete(socket.data.user.id);
    io.emit('presence', [...online]);
  });
});

5. Масштабування на кілька процесів

Проблема: якщо серверів кілька, користувачі на різних інстансах не бачать подій одне одного (кожен тримає свій список сокетів у памʼяті). Рішення — adapter, що пересилає події між інстансами через спільний брокер (Redis):

import { createAdapter } from '@socket.io/redis-adapter';
import { createClient } from 'redis';

const pub = createClient({ url: process.env.REDIS_URL });
const sub = pub.duplicate();
await Promise.all([pub.connect(), sub.connect()]);

io.adapter(createAdapter(pub, sub)); // тепер broadcast працює між усіма інстансами

Ще один наслідок кількох інстансів — sticky sessions: балансувальник має слати запити одного клієнта на той самий сервер (бо long-polling fallback тримає стан). Redis-adapter + sticky sessions — стандартна пара для продакшену.
