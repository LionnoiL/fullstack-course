1. Middleware

Middleware — код, що виконується перед процедурою: перевірити права, залогувати, зміряти час. Він отримує ctx і викликає next(), щоб пустити запит далі (або кидає помилку, щоб зупинити).

// server/trpc.ts
const t = initTRPC.context<Context>().create();

const logger = t.middleware(async ({ path, type, next }) => {
  const start = Date.now();
  const result = await next();
  console.log(`${type} ${path} — ${Date.now() - start}ms`);
  return result;
});

export const publicProcedure = t.procedure.use(logger);

2. Захищені процедури

Найчастіший middleware — перевірка автентифікації. Він читає ctx.user (який ми поклали в контекст) і або кидає UNAUTHORIZED, або пускає далі. Ключовий трюк: next() може звузити тип контексту — після перевірки ctx.user уже не null.

import { TRPCError } from '@trpc/server';

const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.user) {
    throw new TRPCError({ code: 'UNAUTHORIZED' });
  }
  // передаємо далі звужений контекст: user тепер точно є
  return next({ ctx: { user: ctx.user } });
});

export const protectedProcedure = t.procedure.use(isAuthed);
// тепер у процедурі ctx.user — гарантовано не null
me: protectedProcedure.query(({ ctx }) => ctx.user),
deleteAccount: protectedProcedure.mutation(({ ctx }) => db.users.remove(ctx.user.id)),

Патерн «базові процедури» дуже зручний: publicProcedure для відкритих ендпоінтів і protectedProcedure для тих, що вимагають входу. Захист — в одному місці, а не розсипаний перевірками по кожній процедурі.

3. Помилки: TRPCError

Помилки кидають через TRPCError зі стандартним code, який tRPC перекладає у HTTP-статус. Основні коди:

  • BAD_REQUEST (400) — некоректні дані (Zod кидає це сам);
  • UNAUTHORIZED (401) — не автентифікований;
  • FORBIDDEN (403) — немає прав;
  • NOT_FOUND (404) — ресурс не знайдено;
  • INTERNAL_SERVER_ERROR (500) — інше.
byId: publicProcedure
  .input(z.object({ id: z.number() }))
  .query(({ input }) => {
    const todo = db.todos.findById(input.id);
    if (!todo) throw new TRPCError({ code: 'NOT_FOUND', message: 'Немає такої задачі' });
    return todo;
  }),

На клієнті ця помилка приходить типізовано: error.data?.code === 'NOT_FOUND', а error.message містить текст.

4. Формат помилок і Zod

Через errorFormatter в initTRPC можна долучати до відповіді деталі Zod-помилок, щоб клієнт показав їх по полях (як у формах):

const t = initTRPC.context<Context>().create({
  errorFormatter({ shape, error }) {
    return {
      ...shape,
      data: {
        ...shape.data,
        zodError: error.cause instanceof ZodError ? error.cause.flatten() : null,
      },
    };
  },
});

5. Коротко: коли натомість GraphQL

tRPC блищить у внутрішньому TypeScript-фулстеку. Якщо ж API публічний, потрібні клієнти іншими мовами або гнучкі запити «візьми лише ці поля» під різні екрани — подивись у бік GraphQL (схема SDL, один ендпоінт, кодогенерація типів). Це не конкуренти на кожен проєкт, а різні інструменти під різні контракти.

6. Підсумок розділу

  • middleware виконується перед процедурою й може звужувати контекст;
  • protectedProcedure централізує перевірку автентифікації;
  • помилки — через TRPCError з кодом; на клієнті вони типізовані;
  • tRPC — для TS-монорепо; публічний контракт — REST/GraphQL.
